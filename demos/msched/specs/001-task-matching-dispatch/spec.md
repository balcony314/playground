# Feature Specification: 任务撮合调度

**Feature Branch**: `001-task-matching-dispatch`

**Created**: 2026-07-14

**Status**: Draft

**Input**: User description: "待处理任务自动匹配给有能力处理的工作节点并下发执行（系统核心撮合派发）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 待处理任务匹配下发 (Priority: P1)

业务方有大量待处理任务，每个任务携带能力要求（描述需要何种能力的工作节点执行）。
系统自动把这些待处理任务匹配给能力满足其要求的在线工作节点，放入该节点的待拉取队列
等待其主动拉取执行。匹配过程持续进行，新任务创建后即可参与撮合，无需等待人工调度或定时触发。

**Why this priority**: 这是整个调度系统的核心价值--让海量任务被合适的工作节点自动接走执行。
没有撮合派发，任务永远停留在待处理状态，系统无意义。

**Independent Test**: 创建一批携带能力要求的待处理任务，以及一批携带对应能力标签的在线工作节点，
启动撮合，验证每个任务被匹配放入能力满足的节点待拉取队列。

**Acceptance Scenarios**:

1. **Given** 一个待处理任务（能力要求为 R）与一个在线工作节点（能力标签满足 R），
   **When** 系统执行撮合，**Then** 该任务被放入该工作节点的待拉取队列并标记为已调度待拉取。
2. **Given** 一个待处理任务（能力要求为 R）且当前无任何在线工作节点能力标签满足 R，
   **When** 系统执行撮合，**Then** 该任务转入退避态而不被丢弃，待后续有匹配节点时重新参与撮合。
3. **Given** 多个能力要求与优先级不同的待处理任务，**When** 系统撮合，**Then** 高优先级任务先被
   匹配派发，同优先级任务按创建顺序先创建先派发。

---

### User Story 2 - 多租户公平防饿死 (Priority: P2)

多个租户组同时拥有大量待处理任务，且共享同一批工作节点。系统按租户组轮询撮合，确保
各组任务都能被持续推进，不因某个租户组任务量巨大而让其他组任务长期等待甚至饿死。

**Why this priority**: 多租户隔离公平是生产级调度系统的基本要求，避免" noisy neighbor"
挤占资源。但优先级低于核心撮合本身--先能撮合，再谈公平。

**Independent Test**: 创建两个租户组，A 组有大量任务、B 组有少量任务，共享同一批工作节点，
持续撮合，验证两组任务都被持续推进，B 组不被 A 组饿死。

**Acceptance Scenarios**:

1. **Given** 租户组 A 有大量待处理任务、租户组 B 有少量待处理任务，且二者共享工作节点池，
   **When** 系统持续撮合，**Then** A 与 B 的任务均被持续推进，B 组任务不被 A 组长期饿死。
2. **Given** 某租户组当前无可匹配的在线工作节点，**When** 系统轮询到该组，**Then** 跳过该组
   继续撮合其他组，不因该组空转而阻塞整体推进。

---

### User Story 3 - 防双发与节点容错 (Priority: P3)

多调度节点对等运行，可能并发尝试撮合同一个任务。系统保证同一任务不会被重复派发给多个
工作节点；任一调度节点离线后，其原归属的任务由其他节点接管撮合，不丢失不重复。

**Why this priority**: 防双发与容错是分布式正确性底线，避免任务被重复执行或因节点故障丢失。
优先级 P3 因其依赖核心撮合（US1）与多节点对等（属部署形态）已就绪后才有意义。

**Independent Test**: 启动多个调度节点并发撮合同一批任务，验证每个任务仅被一个节点成功占用、
零重复下发；停掉其中一个节点，验证其原属任务被其他节点接管且不重复。

**Acceptance Scenarios**:

1. **Given** 多个调度节点并发尝试撮合同一待处理任务，**When** 抢占发生，**Then** 该任务仅被
   其中一个节点成功占用并派发，不会被重复下发到多个工作节点。
2. **Given** 某调度节点离线，**When** 其原归属任务到达处理时机，**Then** 由其他存活的调度节点
   接管撮合，任务不丢失且不被重复派发。

---

### Edge Cases

- 任务的能力要求无任何在线工作节点满足时：转入退避态，按退避策略等待重试，永不放弃。
- 工作节点在任务已入其待拉取队列但尚未被拉取时下线：任务在派发超时后被重新撮合回待处理，
  可被其他匹配节点接走。
- 多调度节点对同一活跃租户组并发撮合：靠防双发保证同一任务不重复派发。
- 任务被反复派发（派发后始终未被有效接走或执行）累计超限：转入丢弃态，不再参与撮合。
- 全部工作节点离线：所有任务转入退避态等待，工作节点恢复后恢复撮合，不丢失任务。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 将待处理任务匹配给能力标签满足任务能力要求的在线工作节点。
- **FR-002**: 匹配成功后系统 MUST 将任务放入对应工作节点的待拉取队列，并标记为已调度待拉取。
- **FR-003**: 系统 MUST 保证同一任务不会被重复派发给多个工作节点（防双发）。
- **FR-004**: 系统 MUST 按租户组轮询撮合，防止单一活跃租户组饿死其他组的任务推进。
- **FR-005**: 系统 MUST 支持业务自定义任务的能力要求维度（任意 key-value 标签约束），维度开放。
- **FR-006**: 当无在线工作节点满足任务能力要求时，系统 MUST 将任务转入退避态；退避到期后重新
  参与撮合，且 MUST 永不放弃（不因长期无匹配而丢弃任务）。
- **FR-007**: 系统 MUST 按任务优先级与创建顺序撮合：高优先级先派发，同优先级按创建时间先创建先派发。
- **FR-008**: 系统 MUST 支持多调度节点对等运行，任一节点故障 MUST NOT 影响整体撮合可用性，
  其原归属任务由其他节点接管。
- **FR-009**: 任务派发次数累计超过上限时系统 MUST 将其转入丢弃态，不再参与撮合。
- **FR-010**: 系统 MUST 仅对在线（心跳活跃）的工作节点进行匹配，已离线节点不参与撮合。

### Key Entities *(include if feature involves data)*

- **Task**: 业务工作单元。关键属性：所属租户组、能力要求（selector）、优先级、最大执行时长、
  当前状态、派发次数。任务由业务方创建，创建即待处理即可参与撮合。
- **Worker**: 在线工作节点。关键属性：能力标签（labels）、在线状态、注册心跳。节点主动拉取
  其待拉取队列中的任务执行。
- **Dispatch Queue**: 每个工作节点按租户组分桶的已调度待拉取队列。撮合成功者将任务放入对应
  节点对应租户组的桶中，节点拉取时按租户组轮询各取一个。
- **GroupUID**: 租户隔离与公平调度的分组维度。既是任务隔离边界，也是防饿死轮询的轮询单元。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 待处理任务在匹配到合适的在线工作节点后，在数秒内进入该节点的待拉取队列。
- **SC-002**: 系统在 10 亿级待处理任务总量下持续撮合下发，规模增长 MUST NOT 导致撮合停滞或
  显著变慢。
- **SC-003**: 同一任务在多节点并发撮合下零重复下发（重复下发率 = 0）。
- **SC-004**: 多个租户组并发拥有大量待处理任务时，各组任务均能被持续推进，无租户组被长期饿死
  （各组任务推进量在观察期内均非零）。
- **SC-005**: 任一调度节点离线后，其原归属任务由其他节点接管，不丢失（任务总量守恒）且不重复。
- **SC-006**: 无匹配在线工作节点的任务在节点恢复后能被重新撮合派发，不因曾退避而永久丢失。

## Assumptions

- 工作节点通过主动拉取获取已调度任务（非系统推送），拉取的阻塞/退避语义属另一功能范围。
- 任务创建即为待处理、立即可参与撮合；不支持定时调度（无调度时间字段）。
- 能力要求为单向硬约束（任务能力要求 ⊆ 节点能力标签），不支持软偏好打分或加权匹配。
- 工作节点容量模型与背压不在本功能范围；节点过载由其拉取水位与心跳机制处理。
- 多租户公平为隔离级防饿死（按租户组轮询），非长期严格等量派发（各组待派量不等、节点速度差异
  会导致合理偏斜）。
- 退避任务到期后被撮合查询自然取到重新参与，不主动唤醒。
- 退避策略参数（起始间隔、封顶、抖动）与派发次数上限的具体数值由配置给定，本功能不固化。
- 撮合吞吐与规模相关的性能目标待硬件压测后校准回填。
